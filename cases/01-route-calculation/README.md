# Контекст

## Как было до системы

Документы с маршрутом готовили в Excel: заполняли вручную, печатали, подписывали. Единого процесса не было — каждый заполнял по-своему, данные не сохранялись в единой системе.

**Рекомендуемый маршрут не строился в принципе.** Построение пути лежало исключительно на водителе: он ехал «как знает» или по картам. Никто не проверял, легален ли этот путь для конкретной машины.
Если на предполагаемом пути встречался знак, ограничивающий проезд по типу транспортного средства (например, запрет движения грузовиков или движения с прицепом), водитель узнавал об этом уже в пути. Маршруты могли плутать, машина шла в объезд или под знак. Отсюда риск штрафов, срывов сроков и лишнего километража.

## Что нужно было решить

При переносе процесса в систему ключевой вопрос был: **как рассчитывать маршрут, который учитывает ПДД и параметры конкретного транспортного средства, а не оставлять это на ответственность водителя**.

Варианты:
**Оставить ручной ввод** — просто, но риск штрафов и нарушений остаётся, ответственность по-прежнему на водителе.
**Считать самим** — строить маршруты с учётом всех знаков и ограничений. Слишком сложно и требует постоянного обновления данных.
**Интегрироваться с внешним сервисом маршрутизации** — сервис уже умеет строить маршруты по ПДД, учитывать тип транспорта и его параметры (вес, габариты, прицеп).

Выбрали третий вариант: внешний сервис возвращает не просто «расстояние», а **маршрут, который машина может проехать легально**.

## Решение

При создании документа сотрудник выбирает точки маршрута (начало, промежуточные, конец), тип транспорта и его параметры (вес, габариты, наличие прицепа и т.д.). Система обращается к внешнему сервису маршрутизации и автоматически подставляет в документ расстояние, рассчитанное с учётом ПДД для данного типа транспорта. Сотрудник может скорректировать значение вручную.

## Пользователи

- Сотрудник, создающий документ — видит расчёт, может скорректировать.
- Водитель — получает документ с маршрутом, который разрешен для его ТС.
